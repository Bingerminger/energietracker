# Installation & operation

**English** · [Deutsch](../../technical/01-installation.md)

[← Compendium index](../README.md)

Energietracker is deliberately **dependency-free**: no Composer, no npm build, no
database, no external service at runtime — apart from the temperature sync with
Open-Meteo (since v2.8.0 automatically once a day, can be switched off under
*Settings → Fill weather automatically*). A PHP-capable web server and a browser
are enough.

---

## 1. Requirements

| Component | At least | Recommended | Purpose |
|---|---|---|---|
| PHP | 8.1 | 8.4 | backend runtime |
| PHP extensions | `json`, `mbstring` *(optional)* | ditto | JSON store; `iconv` for PDF umlauts |
| Web server | PHP built-in server | Apache/nginx | delivery |
| Browser | a current Chromium/Firefox/Safari | ditto | SPA frontend (ES modules) |
| Python | 3.9 | 3.11 | only for the optional Excel import (`scripts/init_data.py`) |

**No** PHP packages via Composer are needed. The PDF report is generated by a
custom, built-in PDF writer — no mPDF, no `gd`. `iconv` (part of most PHP
distributions) is used for the correct umlaut rendering in the PDF; if it is
missing, the report stays functional and umlauts are then simplified.

Python is **only** needed if measurements are to be imported from an Excel file
(`scripts/init_data.py`, requires `openpyxl` — see `requirements.txt`). For
running the app itself, Python is not required.

## 2. Quick start (local test)

```bash
# 1. Unpack / clone the repository
cd energietracker

# 2. Start with the built-in PHP server — always with router.php
php -S 127.0.0.1:8080 router.php

# 3. Open the browser
#    http://127.0.0.1:8080
```

> Without `router.php` the built-in server serves **every** file, including
> `data/` with all user data. And only start it on `127.0.0.1` — it is meant for
> development, not for others on the network.

On first access the **migrator** automatically creates the data structure under
`data/` and raises it to the current schema (**1.6.0**). No manual step is
needed. A completely empty directory has been recognised as a first start since
v1.9.1 and initialised with default meters (gas/electricity/water).

### Load demo data

Under `demo-data/` the repository contains a complete example dataset for **all
eight** utilities (gas, electricity, water, district heating, heating oil,
pellets, PV feed-in, PV generation), including realistic tank sizes and delivery
cadence. The most convenient way to load it is directly in the app via
**Settings → Load demo data** (F1007). Alternatively via the file system:

```bash
# Replace the data directory with the demo data (caution: overwrites!)
rm -rf data && cp -r demo-data data
php -S 127.0.0.1:8080 router.php
```

The demo data carries `schema_version: 1.1.0` and is automatically migrated to
the current state on first start (additive, lossless). The migration path
(1.0.0 → current schema) is still safeguarded, now via a separate migration smoke
test in the CI instead of via the demo start.

## 3. Production operation

### 3.1 Apache

`api.php` is the API entry point, `index.php` delivers the SPA shell. The
frontend calls the API as `api.php/api/…` and navigates by hash route (`#/…`) —
no rewrite rules for the API or the SPA are needed.

The **bundled `.htaccess`** (since v2.6.0) blocks everything that is not meant
to be served — `data/` (user data, backups), `src/`, `tests/`, `docs/`,
`.git/` and all dotfiles, project files such as `composer.json` or `*.md` —,
passes the `Authorization` header on to PHP-FPM (for the Home Assistant token)
and sets the cache headers. `data/.htaccess` is the second safeguard.
Prerequisites:

- `AllowOverride` at least `FileInfo` for the project directory (the default in
  Synology Web Station),
- `mod_rewrite`, `mod_headers`, `mod_setenvif`.

Additionally possible in the VirtualHost:

```apache
<Directory "/path/to/energietracker/data">
    Require all denied
</Directory>
```

Check that the rules apply:
[Security → web server](08-security.md#9-web-server-what-must-not-be-served).

### 3.2 nginx (outline)

```nginx
location /     { try_files $uri /index.php?$query_string; }
location ~ ^/(data|src|tests|scripts|docker|docs|vendor|demo-data)/ { return 404; }
location ~ /\. { return 404; }
location ~ ^/api(\.php)?(/|$) { fastcgi_pass …; include fastcgi_params; }
```

The complete, tested rule set is in `docker/nginx.conf`.

### 3.3 Write permissions

The web server user needs **write permission** on `data/` (including
`data/backups/`). Writing requests run one after another (lock on
`data/.write.lock`, since v2.5.3), and every file is written atomically
(temporary file, then rename; since v2.6.0 with `fsync` first) — an abort in
mid-write leaves no half-written file. The system diagnostics (`Settings → Diagnostics`, or
`GET /api/diagnostics`) show whether the write permissions are set correctly.

### 3.4 Moving the data directory (`ET_DATA_DIR`)

By default the JSON store sits under `./data` relative to `api.php`. Since
**v1.4.4** the environment variable `ET_DATA_DIR` can force an arbitrary absolute
path — useful for separate data/code mounts, several instances or read-only code
deployments:

```bash
ET_DATA_DIR=/srv/energietracker-data php -S 127.0.0.1:8080 router.php
```

With Apache via `SetEnv ET_DATA_DIR /srv/…` in the VirtualHost, with nginx +
PHP-FPM via `fastcgi_param ET_DATA_DIR /srv/…;`. If the variable is missing, the
default path `./data` remains — fully backward-compatible. The `realpath`
traversal protection in `JsonStore` (also v1.4.4) applies independently of the
chosen directory.

## 4. Data backup

There are three complementary mechanisms:

1. **Full JSON backup** (`Settings → Backup`): a single JSON file in format `3.0`
   that contains *all* utilities, meters, contracts, deliveries, temperatures and
   settings and is re-importable. This is the authoritative backup format.
2. **Snapshot**: places a copy in the data directory under `data/backups/` —
   useful before risky actions. One is created automatically before every backup
   import (`pre-restore-…`) and, since **v2.5.3**, before every schema migration
   during an update (`pre-migration-<old version>_…`). Up to v2.5.2 this section
   claimed the migration snapshot although it did not exist.
3. **CSV export**: tabular per dataset (monthly overview, meter readings or
   deliveries, temperature series) for Excel/LibreOffice — supplementary, **not**
   intended as a full backup (not re-importable).

Simply copying the entire `data/` directory is also a complete backup.

## 5. Updating to a new version

1. **Export a backup** (*Settings → Export backup*) or copy the `data/`
   directory. This is the only way back: a schema migration cannot be undone.
2. **Read the CHANGELOG** — whatever is listed under “Migration” applies to you.
3. Replace the program files (everything except `data/`). Docker:
   [Performing updates](07-docker.md#performing-updates).
4. Open the app in the browser — the migrator raises the schema automatically and
   idempotently as needed. Since v2.5.3 it first stores a snapshot in
   `data/backups/`. If the snapshot fails (e.g. disk full), the migration still
   runs and the log reports it — hence step 1.

A downgrade to an older schema version is **not** supported; newer utilities
would be ignored by old versions. The way back is only the old program version
**and** the backup from step 1.

Migration from an old private **v0.9.0** backup: see
[Migration from v0.9.0](../MIGRATION-FROM-V090.md).

## 6. Optional Excel import

If you want to take over existing data from an Excel file:

```bash
pip install -r requirements.txt        # only openpyxl
python scripts/init_data.py --help
```

The script reads meter readings from an `input.xlsx` (separate tabs per utility)
and temperature CSVs. Details in the script header. For ongoing operation this is
not needed — data can also be fully maintained via the UI.

## Docker operation

From **v1.7.3** there is an official multi-arch image
(`ghcr.io/bingerminger/energietracker`, `linux/amd64` + `linux/arm64`). The
fastest start:

```bash
docker compose up -d        # → http://localhost:8080
```

A detailed, beginner-friendly guide (volumes, updates, logs, environment
variables, troubleshooting) is in its own chapter:
**[Docker operation (for beginners)](07-docker.md)**.
